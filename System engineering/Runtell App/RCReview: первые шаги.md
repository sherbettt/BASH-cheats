## Проблема: разница сетей

### Схема сети из реального примера

```
Ваш ноутбук (Think)
├── IP: 192.168.92.94/24
├── Шлюз: 192.168.92.254
└── Сеть: 192.168.92.0/24

    ↓ (WiFi подключение)

Шлюз/DMZ (dmzgateway1)
├── IP: 192.168.92.253 (доступ из сети 92)
├── IP: 192.168.87.253/24 (сеть DMZ)
└── Сеть: 192.168.87.0/24

    ↓

Сеть RCR
├── Сеть: 192.168.96.0/23
└── Сервер: 192.168.97.152

    ↓

Приложение rcreview-api
└── Порт: 8080
```

### В чем проблема?
Ваш ноутбук (192.168.92.94) **не имеет маршрута** до сети 192.168.96.0/23, поэтому не может обратиться к серверу 192.168.97.152:8080 напрямую.

**Проверка:**
```bash
# На вашем ноутбуке
ip r s
```
Вывод покажет только вашу локальную сеть:
```
default via 192.168.92.254 dev wlan0
192.168.92.0/24 dev wlan0 proto kernel scope link src 192.168.92.94
```

## Способ 1: SSH-туннель (рекомендуемый)

### Что такое SSH-туннель?
SSH-туннель создает защищенный канал, перенаправляющий трафик с локального порта на удаленный сервер через существующее SSH-соединение.

### Как это работает

```
Ваш ноутбук                    Сервер RCR (192.168.97.152)
     │                              │
     │  SSH-соединение              │
     │  (уже установлено)           │
     │                              │
     ├── localhost:8080             │
     │  (браузер)                   │
     │                              │
     └──> SSH-туннель ──────────────> rcreview-api (127.0.0.1:8080)
          (перенаправляет)           (локальный сервис)
```

### Базовая команда

```bash
ssh -L [локальный_порт]:[удаленный_хост]:[удаленный_порт] [пользователь]@[сервер]
```

**Реальный пример:**
```bash
ssh -L 8080:127.0.0.1:8080 root@192.168.97.152
# или через алиас
ssh -L 8080:127.0.0.1:8080 root@rcr
```

### Расшифровка команды
| Параметр | Значение |
|----------|----------|
| `-L` | Создаем локальный туннель (Local) |
| `8080` (первый) | Порт на вашем компьютере для доступа |
| `127.0.0.1:8080` | Куда перенаправлять на сервере |
| `root@192.168.97.152` | SSH-доступ к серверу |

### Доступ к сервису
После запуска туннеля открывайте в браузере:
```
http://localhost:8080
```

### Расширенные опции SSH-туннеля

```bash
# Фоновый режим (туннель работает в фоне)
ssh -f -N -L 8080:127.0.0.1:8080 root@rcr

# Множественные туннели (несколько портов)
ssh -L 8080:127.0.0.1:8080 -L 5432:127.0.0.1:5432 root@rcr

# Туннель через промежуточный хост (ProxyJump)
ssh -J root@dmzgateway1 -L 8080:127.0.0.1:8080 root@rcr

# Туннель с привязкой ко всем интерфейсам
ssh -L 0.0.0.0:8080:127.0.0.1:8080 root@rcr
```

### Преимущества SSH-туннеля
✅ **Безопасность** — весь трафик шифруется SSH  
✅ **Не требует прав администратора** на сервере  
✅ **Не нужно открывать порты** в файрволе  
✅ **Работает через любой SSH-доступ**  
✅ **Не требует настройки маршрутизации**  
✅ **Обходит межсетевые экраны**  

### Недостатки
❌ Туннель активен только пока открыто SSH-соединение  
❌ Нужно держать терминал открытым (или использовать `-f`)  
❌ Дополнительная задержка из-за шифрования (минимальная)

## Способ 2: Добавление маршрута (прямой доступ)

### Что такое маршрутизация?
Маршрутизация указывает операционной системе, через какой шлюз (роутер) отправлять пакеты в определенные сети.

### Проверка текущих маршрутов

**На вашем ноутбуке:**
```bash
ip r s
```
Вывод:
```
default via 192.168.92.254 dev wlan0 proto dhcp src 192.168.92.94 metric 600 
192.168.92.0/24 dev wlan0 proto kernel scope link src 192.168.92.94 metric 600
```

**На шлюзе dmzgateway1:**
```bash
ip r s
```
Вывод:
```
default via 192.168.87.1 dev eth0 proto kernel onlink 
192.168.45.0/24 dev eth2 proto kernel scope link src 192.168.45.253 
192.168.46.0/24 dev eth1 proto kernel scope link src 192.168.46.253 
192.168.87.0/24 dev eth0 proto kernel scope link src 192.168.87.253
```

**Видим:** Нет маршрута до сети 192.168.96.0/23 ни на ноутбуке, ни на шлюзе!

### Добавление маршрута на вашем ноутбуке

**Команда:**
```bash
sudo ip route add [сеть/маска] via [шлюз]
```

**Реальный пример:**
```bash
sudo ip route add 192.168.96.0/23 via 192.168.92.254
```

**Важно!** Для сети /23 адрес должен быть четным:
- ✅ Правильно: `192.168.96.0/23` (диапазон: 192.168.96.0-192.168.97.255)
- ❌ Неправильно: `192.168.97.0/23` (ошибка: Invalid prefix)

### Проверка добавленного маршрута
```bash
ip r s
```
Теперь видим новый маршрут:
```
default via 192.168.92.254 dev wlan0 proto dhcp src 192.168.92.94 metric 600 
192.168.92.0/24 dev wlan0 proto kernel scope link src 192.168.92.94 metric 600 
192.168.96.0/23 via 192.168.92.254 dev wlan0    # ← Новый маршрут!
```

### Проверка доступности
```bash
ping -c 2 rcr
# или
ping -c 2 192.168.97.152
```
Ожидаемый вывод:
```
PING rcr (192.168.97.152) 56(84) bytes of data.
64 bytes from rcr (192.168.97.152): icmp_seq=1 ttl=62 time=94.2 ms
64 bytes from rcr (192.168.97.152): icmp_seq=2 ttl=62 time=115 ms
```

### Теперь можно обращаться напрямую
```bash
curl http://192.168.97.152:8080/
```
Или открыть в браузере:
```
http://192.168.97.152:8080
```

### Как сделать маршрут постоянным

**Вариант 1: Через /etc/network/interfaces**
```bash
# Добавьте в файл /etc/network/interfaces
up ip route add 192.168.96.0/23 via 192.168.92.254
```

**Вариант 2: Через NetworkManager**
```bash
nmcli connection modify "YourWiFi" +ipv4.routes "192.168.96.0/23 192.168.92.254"
```

**Вариант 3: Создать скрипт в /etc/network/if-up.d/**
```bash
#!/bin/bash
ip route add 192.168.96.0/23 via 192.168.92.254
```

### Что если маршрут не работает?

Проверьте IP-форвардинг на шлюзе:
```bash
# На dmzgateway1
cat /proc/sys/net/ipv4/ip_forward
# Должно быть 1, если нет - включите:
echo 1 > /proc/sys/net/ipv4/ip_forward
```

Добавьте маршрут на шлюзе, если его нет:
```bash
# На dmzgateway1
ip route add 192.168.96.0/23 via 192.168.87.1
```

## Сравнение способов

| Критерий | SSH-туннель | Добавление маршрута |
|----------|-------------|---------------------|
| **Сложность** | Низкая (одна команда) | Средняя (нужно знать сеть) |
| **Безопасность** | Высокая (шифрование) | Низкая (трафик открыт) |
| **Требует прав** | Нет (обычный пользователь) | Да (sudo) |
| **Временный/Постоянный** | Временный (пока сессия) | Может быть постоянным |
| **Обход файрвола** | Да (через SSH) | Нет (нужен открытый порт) |
| **Скорость** | Медленнее (шифрование) | Быстрее (прямой доступ) |
| **Зависимость от сети** | Только SSH доступ | Нужен правильный маршрут |
| **Когда использовать** | Разработка, тестирование | Продакшен, постоянный доступ |

## Практические примеры

### Пример 1: Быстрый доступ для разработки
```bash
# Открываем туннель и сразу запускаем браузер
ssh -f -N -L 8080:127.0.0.1:8080 root@rcr && open http://localhost:8080
```

### Пример 2: Множественные сервисы
```bash
# API, база данных, Redis
ssh -L 8080:127.0.0.1:8080 \
    -L 5432:127.0.0.1:5432 \
    -L 6379:127.0.0.1:6379 \
    root@rcr
```

### Пример 3: Использование с ProxyJump
```bash
# Если нет прямого доступа к серверу
ssh -J root@dmzgateway1 -L 8080:127.0.0.1:8080 root@rcr
```

### Пример 4: Настройка в .ssh/config

Добавьте в `~/.ssh/config`:
```
Host rcr-tunnel
    HostName rcr
    User root
    LocalForward 8080 127.0.0.1:8080
    LocalForward 5432 127.0.0.1:5432
```

Теперь достаточно:
```bash
ssh rcr-tunnel
```

## Вывод

**SSH-туннель** — идеальный выбор для:
- Разработки и отладки
- Безопасного доступа
- Временных подключений
- Обхода сетевых ограничений
